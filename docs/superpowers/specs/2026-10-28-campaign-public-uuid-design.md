# Campaign public UUID design

Campaigns keep their numeric `campaigns.id` as an internal relational key. A
unique, immutable `campaigns.public_id UUID` is generated by PostgreSQL for
every existing and new campaign. The user-facing `ordinal` remains a per-chat
number such as “Kampanya 2”.

Every client-facing campaign identifier is the UUID string: REST paths and
filters, chat and tracking JSON, turn results, and live SSE events. The API
resolves a UUID to the internal key at its boundary. Numeric campaign IDs are
not accepted at that boundary. Version and delivery IDs remain internal
numbers where their existing API contract requires them.

The migration backfills existing campaigns without changing any foreign key or
delivery. UUIDs are unique and generated for later inserts. The HTTP layer
uses an explicit mapping from internal IDs to public UUIDs for turn events and
results; the LLM and store continue to use internal IDs.

Verification covers migration of existing records, REST and SSE identity
shapes, unknown UUIDs, frontend routing and selection, and the full test
suite. UUIDs make public URLs harder to guess; they do not replace
authentication or authorization, which this fake-data case does not provide.
